# 管理画面のレコード編集における楽観的ロック — 仕様

この実装のスコープ：共有ツールキット、商品（ツールキットへの
リファクタ）、クーポン、カテゴリー、タグ。それ以外は理由とともに
「対象外」に挙げています。

## 1. 問題

2人の運用者（あるいは1人の運用者が2つのタブで、あるいは運用者と
スイート）が同じレコードを開き、それぞれ独立に編集して保存すると：
2番目の保存が1番目を静かに上書きします。2番目の編集者が1番目の
編集者の値を見たことがない、という事実はデータベースのどこにも
残りません。対策は、古い保存を拒否し、運用者に最新のレコードを
見せ、意図的に再適用できるようにしなければなりません。

これは、削除後の更新の振る舞いの「レコード編集版」です：進んで
しまったレコードへの保存は、明確な拒否（競合または未存在）と
ならなければならず、静かな成功になってはならず、復活に
なってもいけません。

## 2. このコードベースの既存の実践

この考え方はすでに3か所で実証済みです；本機能は新しい形を
発明するのではなく、そのうち最初のものを一般化します。

- **商品（旗艦）。** 編集フォームは、開いた時点の `updated_at` を
  `expected` という名前の隠しフィールド（エポックマイクロ秒）
  として持ちます。`update_product` は書き込みトランザクションの
  中で `SELECT updated_at ... FOR UPDATE` により行を読み戻して
  比較します：不一致なら `AppError::Conflict` を返し、
  コントローラはフラッシュ
  「この商品は既に更新されています。最新の内容を確認
  してから保存してください。」とともに編集ページへリダイレクト
  して応答し、ページは新しい値を再読み込みします。バリエーションは
  同じトランザクションに乗るため、同じチェックで守られます。
- **注文ステータスのフォーム**は `expected` = 運用者が見た
  ステータスを持ち、チェックはステータス自体に対して走ります。
- **返金フォーム**は `expected_refunded_yen` を持ち、決済サービスが
  支払いの前に金額を再チェックします。

## 3. パターン（中核の機能）

1. **トークン。** レコードの `updated_at` をエポックマイクロ秒で
   表したもの。新しいバージョン列は作りません：このコードベースは
   すでにこのトークンを選んでおり、データベースの時計（`now()`）が
   唯一の情報源で、マイクロ秒の分解能により偶然の一致は実務上
   問題になりません。ガード対象テーブルへの書き込みはすべて
   `updated_at = now()` をセットします — アーカイブや
   有効化／無効化のようなステータスの切り替えも含みます — ので、
   いかなる変更も開いているフォームを無効にします。
2. **フォームの往復。** 編集ビューは `expected: String`
   （作成フォームでは空）を持ち、テンプレートは
   `{% if !expected.is_empty() %}<input type="hidden" name="expected" value="{{ expected }}">{% endif %}`
   を出力します。これは現在の商品フォームとまったく同じです。
3. **無い場合は古いクライアントとして扱う。** `expected` の無い
   投稿はチェックをスキップします。これは商品フォームが
   アップグレード用フィールドに対して、またチェックアウトが
   確認フィンガープリントに対して、すでに文書化して取っている
   立場と同じです。現在のフォームは常時このフィールドを送ります；
   この逃げ道は、デプロイ前に描画されたフォームがレコードを
   壊さないためだけに存在します。
4. **トランザクションの中でのチェック。** サービスは書き込み
   トランザクションを開き、次にリポジトリの
   `*_updated_at_for_update(tx, id)`（`SELECT updated_at ...
   FOR UPDATE`）を呼びます。これは現在のトークンを読むと同時に
   行をロックし、競合する2つの保存はこの地点で直列化されます。
   `app/src/concurrency.rs` の共有判定は次のように分類します：
   - `Fresh` — トークンが一致：書き込みを進めます。
   - `Stale` — 行は存在するがトークンが動いた：サービスの競合
     エラーで拒否し、
     `crate::messages::stale_record_message(noun)`
     （「この{noun}は既に更新されています。最新の内容を確認して
     から保存してください。」）を持たせます。
   - `Missing` — 行が無い：サービスの既存の未存在の結果
     （商品とクーポンでは実務上到達しません — どちらも物理削除
     されないため — ですが、判定がこれを名指しすることで、
     対応づけが偶然ではなく明示的になります）。
5. **競合時の UX。** 管理画面の規則どおり：競合メッセージを
   フラッシュし、Post/Redirect/Get でそのレコード自身の編集
   ページへ戻します。ページはデータベースから再読み込みします。
   運用者は新しい値を見ます；返ってくるフォームは新しいトークンを
   持つため、意図的な2回目の保存は情報を得たうえでの上書きに
   なります。古い入力を新しいデータの上に静かにマージすることは
   しません。

## 4. 共有ツールキット

- `app/src/concurrency.rs`：`Staleness` 列挙型と `judge`
  関数。モジュールドキュメントに本仕様の規則を記します。
  SQL はレイヤー規則に従い、各リポジトリにテーブルごとに
  置きます（`*_updated_at_for_update`）。
- `crate::messages::stale_record_message(noun)`：唯一の文言で、
  レコードの名詞（商品 / クーポン /
  カテゴリー / タグ）でパラメータ化します。商品パスの既存の
  メッセージは `stale_record_message("商品")` とバイト単位で
  同一です。

## 5. この実装でのエンティティごとの配線

- **商品** — リファクタのみ：`update_product` が `judge` と
  メッセージビルダーを使います。振る舞いは不変（回帰の基準：
  test_admin はベースラインを維持）。
- **クーポン** — 新規。マイグレーションが `updated_at` を追加；
  定義モデルと `find_definition` がそれを持ちます；リポジトリに
  `coupon_updated_at_for_update` が加わり、更新と有効化／無効化の
  書き込みで `updated_at` を進めます；`update_definition` は
  `expected: Option<i64>` を取り、引き換えロックより前に、
  トランザクションの中で最初にチェックします；
  `CouponWriteError` に `Conflict(String)` バリアントが加わります；
  コントローラはフォームの `expected` をパースし、Conflict の
  ときはフラッシュしてクーポン自身のページへリダイレクトします；
  編集フォームのビューとテンプレートが隠しフィールドを持ちます。
- **カテゴリー** — 新規、ただしマイグレーションなし（列が
  すでに存在します）。`update_category` を通す同じ配線で、
  コントローラの Conflict アームがフラッシュして編集ページへ
  リダイレクトします。
- **タグ** — 新規、マイグレーションあり。`update_tag` を通す
  同じ配線です。

## 6. データ変更

マイグレーション `20261101000037_coupon_tag_updated_at.sql`：
`ALTER TABLE coupons ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT now();`
タグについても同様です。既存の行はマイグレーション時点を
トークンとして持ちます；デプロイ後に描画されるフォームは
本物のトークンを持ちます。

## 7. 振る舞いマトリクス（検証で示すべきこと）

| # | シナリオ | 期待結果 |
|---|----------|-----------------|
| T1 | 通常の編集、フォームを開いて1回保存 | 適用される；トークンが前進する |
| T2 | フォームを開いた後、レコードが別の場所で保存され、その後古いフォームを保存 | 競合フラッシュ；レコードは新しい値を保持；編集ページは最新を再読み込み |
| T3 | 2つのセッションが同じレコードを競合 | 最初の保存が適用；2番目は競合 — 勝者はちょうど1つ |
| T4 | `expected` の無い投稿（古いクライアント） | 適用される（文書化された立場、§3.3） |
| T5 | 編集フォームを開いている間にレコードがアーカイブ／切り替え | 保存は競合する（切り替えがトークンを進めた）；商品ではアーカイブ拒否がコントローラで先に発火する |
| T6 | 存在しない id への編集投稿 | 既存の未存在パス、不変 |
| T7 | 引き換えのあるクーポンを古いトークンで編集 | 競合が引き換えロックのエラーに勝つ（古さのチェックが先） |

## 8. 対象外（理由つき）

- **注文と決済** — 主張型のガード（ステータスと金額の期待値）は
  タイムスタンプトークンより強く、その上に第2の仕組みを重ねると
  弱くなります。
- **在庫調整** — 注文確定級トランザクションの中の追記のみの
  台帳エントリ；古くなるフィールド編集が存在しません。
- **店舗設定、ホームコンテンツ、会員の住所** — フェーズ2の
  候補です（設定は独自の形を持つ単一保存；住所は所有者スコープの
  ストアフロント編集で、競合は自己原因のみ）。同じツールキットが
  必要になったときに使えます。
- **CSV インポート** — バッチのプレビュー／適用がすでにバッチ
  状態でガードしています；ファイルアップロードはレコード編集
  フォームではありません。
- **ストアフロントとエージェントの面** — 運用者のレコード編集
  フォームがありません；会員自身の編集は所有者スコープです。

## 9. リスクと限界

- トークンは書き込みパスの正直さ次第です：将来、ガード対象
  テーブルへの UPDATE が `updated_at = now()` を忘れると、
  フォームの無効化が静かに止まります。リポジトリ関数がテーブル
  ごとの唯一の書き込みパスであることが、これを監査可能にして
  います；本仕様はこれを、ガード対象テーブルへの新しい書き込みに
  対する恒常的な規則として名指しします。
- `FOR UPDATE` は保存トランザクションの長さだけ同じ行の書き手を
  直列化します；管理画面の保存は短いため、運用者規模では
  競合は問題になりません。
- これは*保存*同士の更新ロストを防ぎます。履歴のバージョン管理は
  しません：監査ログが、誰が何を変えたかの記録であり続けます。
