# アーキテクチャ

このドキュメントは、コードを眺めただけでは分かりにくい全体構造と
設計判断をまとめた、開発者向けの案内です。個別機能の仕様は
[仕様ドキュメント](../specs/)、書き方の基準は
[Rust ベストプラクティス](RUST_BEST_PRACTICES.md)、テストの進め方は
[テストガイド](TESTING.md) を参照してください。

## 1. システムの全体像

Rust（Axum）製の EC サイトです。ストアフロント（顧客向け画面）、
管理画面、エージェント向け API を1つのサーバーバイナリが担い、
状態は PostgreSQL に集約します。画面は Askama テンプレートで
サーバーサイド描画し、静的アセットと一緒に同じプロセスから
配信します。

動く部品は次のとおりです。

| 部品 | 役割 |
|---|---|
| サーバーバイナリ（`server` クレート） | HTTP 配信とバックグラウンドタスクの起動・監督。役割（`all` / HTTP のみ / タスクのみ）を切り替えられます |
| アプリ本体（`app` クレート） | 画面、業務ロジック、DB アクセスのすべて |
| 設定（`configuration` クレート） | `config.toml` の型付き読み込み。秘密情報は持ちません |
| PostgreSQL | 唯一の永続ストア。起動時にマイグレーションを適用します |
| KOMOJU / Stripe（外部） | カード・コンビニ・PayPay のホスト型決済ページと Webhook。どちらのレールを使うかは設定で切り替えます |
| SMTP（外部） | 注文メール、キャンペーン、ステップメールの送信 |
| SNS プロバイダ（外部） | LINE / Google / Yahoo! のソーシャルログイン |
| LLM（外部、任意） | エージェントチャット／エージェントチェックアウト |

## 2. ワークスペースとディレクトリ構成

Cargo ワークスペースは3クレートで構成されます。

| クレート | 中身 |
|---|---|
| `server` | バイナリ本体。`main.rs`（起動と終了処理）、`background_tasks.rs`（後述の登録原則）、`log_routing.rs`（ログの振り分け）だけの薄い層です |
| `app` | ライブラリ。本体のすべてがここにあります |
| `configuration` | `config.toml` を型付きで読む小さなクレート。秘密情報は環境変数からのみ取得します |

`app/src` の内訳です。

| ディレクトリ／ファイル | 役割 |
|---|---|
| `controllers/storefront/` | 顧客向け画面のハンドラ（商品、カート、チェックアウト、マイページ等） |
| `controllers/admin/` | 管理画面のハンドラ（注文、商品、会員、メール、設定等） |
| `services/` | 業務ロジックの中心。注文・決済・ポイント・メール等の規則はここに置きます（管理画面専用のものは `services/admin/`） |
| `repositories/` | SQL の置き場所。サービスからのみ呼ばれます（管理画面向けは `repositories/admin/` に集約） |
| `models/` | DB 行とドメインの型。決済方法やポイント残高等の定義もここです |
| `views/` | Askama テンプレートへ渡すビューモデルと描画ヘルパー（テンプレート実体は `resources/templates/`） |
| `api/` | 画面を持たない HTTP 入口：決済 Webhook（KOMOJU / Stripe）、エージェント向け API、郵便番号 API、メール開封トラッキング |
| `routes.rs` | ルーターの組み立て（後述） |
| `session.rs` / `session_store.rs` | セッション基盤と現在ユーザーの抽出 |
| `middleware/` | CSRF（発行・検証・ローテーション）、管理画面の IP ガードと権限ガード、ログインスロットル、メンテナンス表示などのミドルウェア群 |
| `pricing.rs` | 税込価格からの税額抽出など、金額計算の共通部品 |
| `messages.rs` | 利用者向け文言の集約先 |
| `error.rs` | アプリ共通エラー型とエラーページへの変換 |
| `util/` | 業務に依らない共通ユーティリティ（CSV 入出力、画像パス、HTML サニタイズ、ページネーション等） |

その他のディレクトリです。

| ディレクトリ | 役割 |
|---|---|
| `resources/` | Askama テンプレート実体（`templates/`）。`storefront/` と `admin/` の下に `layouts/`（共通枠）、`pages/`（画面）、`parts/`（部品）。`static/` に CSS・JS・画像 |
| `migrations/` | DB マイグレーション（後述） |
| `scripts/` | 品質ゲート `check.sh`、E2E スイート群（`tests/`）、開発用スタブ（`stubs/`：KOMOJU / Stripe / SNS / LLM）、運用スクリプト（`ops/`） |

## 3. レイヤーとリクエストの流れ

処理は「コントローラ → サービス → リポジトリ → PostgreSQL」の
一方向で流れます。

- **コントローラ**：HTTP の都合だけを扱います。フォームの受け取り、
  セッションの読み書き、サービスの呼び出し、テンプレート描画です。
  業務規則は書きません。
- **サービス**：業務規則とトランザクション境界の所有者です。
  注文確定のような複合処理は、1つのサービスメソッドが
  1トランザクションで完結させます。
- **リポジトリ**：SQL を発行し、行をモデルに変換します。
  業務判断は持ちません。
- **ビュー**：Askama テンプレートは `app/src/views/` のビューモデルを
  受け取って描画します。金額や税の計算をテンプレート側で
  行うことはありません。

ルーターは `app/src/routes.rs` の `create_router` が組み立てます。
ストアフロント、管理画面、Webhook、エージェント API、アセット、
ヘルスチェックを個別のルーターとして作り、最後にマージします。
セキュリティヘッダ等のレイヤーはマージ後に適用します
（マージ前に付けたレイヤーはマージ先へ届かないためです）。

### セッションと CSRF

セッションは tower-sessions ベースで、ストアフロントと管理画面で
別のセッション層を使います。セッションレコードが持つのは
ログイン中の本人 ID とフロー状態（CSRF トークン、チェックアウトの
途中状態、フラッシュメッセージ等）だけです。

CSRF は `middleware/csrf.rs` のミドルウェアが一元管理します。状態変更リクエスト
ではトークンを検証し、返却 HTML には隠しフィールドとして自動で
埋め込みます。トークンのローテーションは「本人の変化」と
「本人の資格情報の変化（パスワード・メール・二要素認証）」に
追随する設計で、個別のハンドラにローテーションコードは書きません。

管理画面にはさらに IP ガード（`middleware/admin_ip_guard.rs`）と
権限グループによるガード（`middleware/admin_permission_guard.rs`）が掛かります。
会員・管理者の双方に TOTP による二要素認証があります。

## 4. 主要フロー

### 4.1 チェックアウトと決済

1. カート確定後、チェックアウトの途中状態はセッションに保持され、
   配送先・配送枠・支払方法を段階的に選ばせます。支払方法に紐づく
   手数料（代引き手数料）は、その方法が実際に選ばれるまで
   合計には含めません。
2. 注文確定（`order_service`）は1トランザクションで、在庫の引き当て、
   クーポンの利用、ポイントの利用、注文と決済レコードの作成を
   完結させます。決済レコードは `payments.provider` に事業者を
   持ちます（`komoju` / `stripe` / `cod` / `agent`）。
3. ゲートウェイ決済の場合、`payment_service` がセッションを作成し、
   顧客を、設定（`hosted_gateway`）で選択中のゲートウェイ
   （KOMOJU または Stripe）のホスト型決済ページへリダイレクトします。
4. 結果の取り込み口は2つあり、どちらも最終的に
   `apply_provider_payment` という単一の状態適用パスへ合流します。
   - **戻り導線**（`controllers/storefront/payment_return.rs`）：
     ブラウザの戻り自体は何も証明しないため、サーバー側で
     セッションを取り直してから状態を適用します。
   - **Webhook**（`api/komoju_webhook.rs`、`POST /webhooks/komoju`）：
     署名（HMAC-SHA256）は**生ボディに対してパース前に**検証します。
     Webhook 秘密が未設定ならルート自体が 404 を返します。
     重複排除はボディ内のイベント ID をキーに `webhook_events` へ
     記録して行います。
   - **Webhook（Stripe）**（`api/stripe_webhook.rs`、
     `POST /webhooks/stripe`）：`Stripe-Signature`（タイムスタンプと
     生ボディに対する HMAC）をパース前に検証し、5分のリプレイ
     許容を設けます。未設定なら 404、重複排除はイベント ID で
     行い、KOMOJU と同じ単一の状態適用パスへ合流します。
5. 取りこぼしはバックグラウンドの照合スイープ（後述）が拾います。
   未決済レコードの状態確認、放置された決済の失効、そして
   返金後の補償（在庫戻し・ポイント復元）の再試行がここで行われます。
   補償は決済レコードのフラグで管理され、ゲートウェイの有無に
   関わらず再試行されます。

代引き（COD）と、ポイントで全額をまかなう注文はゲートウェイを
通りません。後者は「請求額 0 円の注文」としてその場で決済済みに
なります。

### 4.2 バックグラウンドタスク

定期処理はすべて `server/src/background_tasks.rs` の `start_all` に
登録します（次節の登録原則）。現在のワーカーは次のとおりです。

| ワーカー | 仕事 |
|---|---|
| 決済照合スイープ | 未決済の照合、放置決済の失効、返金補償のリトライ |
| メールキャンペーン | 予約されたキャンペーンの配信（同意済み会員のみ） |
| ステップメール | ウェルカム／レビュー依頼シナリオの進行と送信 |
| 配送メール | 出荷通知の下書き（アウトボックス）の送信 |
| 在庫戻し通知 | 再入荷を待つ会員への通知 |
| 在庫低下アラート | 運営者への通知 |
| カートリマインダー | 放置カートへのリマインドメール |
| ポイント | 付与ロットの失効処理 |
| ゲストカート掃除 | 保持期間を過ぎたゲストカートの削除 |
| セッション掃除 | 期限切れセッションの削除 |
| ログ保持 | 保持期間を過ぎたログファイルの削除 |

各ワーカーはスーパーバイザの下で動き、異常終了時は間隔を広げながら
再起動します。終了時は全ワーカーを並行してドレイン
（進行中の処理の完了待ち）します。

## 5. 主要なシームと設計判断

### 決済ゲートウェイの境界（PaymentGateway トレイト）

サービス層は決済事業者と HTTP で直接話しません。
`app/src/services/payment_gateway.rs` の `PaymentGateway` トレイト
（セッション作成・取得、キャプチャ、取消、返金）が境界で、実装は
`komoju_client.rs` の `KomojuGateway` と `stripe_client.rs` の
`StripeGateway` です。テスト用に台本どおり振る舞う `FakeGateway`
も同じトレイトを実装します。

チェックアウトが提示するのは、設定 `hosted_gateway` で選択中の
レール（既定は `komoju`）だけです。一方、照合・返金・スイープは
決済レコードごとの事業者列で振り分けるため、レール切り替え後も
もう一方のレールで開いた決済はその事業者で最後まで処理されます。
事業者の追加は、このトレイトの実装と、選択肢への事業者名の
追加で行います。方針と比較は、内部の設計資料にまとめています。

### 設定の層分けとフェイルクローズ

- 非秘密の設定は `config.toml` に置き、`configuration` クレートが
  型付きで読みます。ファイルが無い・壊れている場合は起動しません。
- 秘密情報は環境変数からのみ読みます（`.env.example` が一覧です）。
  コードや `config.toml` に秘密は置きません。
- 決済はフェイルクローズです。有効化フラグと秘密情報がそろった
  ときだけゲートウェイが構築され、欠けていれば構築されず、
  チェックアウトは代引きのみを提示します。決済の設定ミスで
  店自体が落ちることはありません。
- 顧客向け URL の生成には `PUBLIC_BASE_URL` を使います
  （決済の戻り先、メール内リンク、SNS ログインのコールバック）。

### バックグラウンドタスクの登録原則

登録コードは `server/src/background_tasks.rs` に集約します。
`main.rs` は `start_all` を1回呼ぶだけで、新しいワーカーを足しても
`main.rs` は太りません。ワーカー本体は各サービス側に
`start_worker` として置き、登録側はそれを名前とともに並べるだけです。

### 金額は整数円

金額は最初から最後まで整数円（`i64`）で扱い、浮動小数点は
使いません。税込価格からの税額抽出は税率クラスごとに
`pricing.rs` の共通処理で行い、画面・帳票・メールで同じ内訳を
出します。

### ポイントは「割引」ではなく支払手段

ポイントは注文合計や税額を変えません。請求額が
「合計 − ポイント利用分」になるだけです。付与は出荷時に、
利用したポイントの基礎額から計算します。失効は付与ロット単位で
管理し、返金時は元のロットへ復元します（失効済みロットへの
復元規則を含む詳細は
内部の設計資料にまとめています）。

### 管理画面の同時編集

管理画面のレコード編集には楽観的ロックを採用し、保存時に
競合を検出して上書きを防ぎます。設計は
[楽観的ロック仕様](../specs/OPTIMISTIC_LOCKING_SPEC.md) を
参照してください。

## 6. データベースの形

テーブルは77あります。スキーマの詳細はマイグレーションが正で、
ここではまとまりだけを示します。

| グループ | 主なテーブル |
|---|---|
| 会員・認証 | `users`、`user_identities`（SNS）、`admins`、パスワードリセット、TOTP 回復コード、メール変更、退会 |
| 商品・カタログ | `products`、`product_variants` とバリエーション軸、`categories`、`tags`、`product_images`、`stock_adjustments` |
| 注文・配送 | `orders`、`order_items`、`order_tax_breakdowns`、`order_shipments`、`return_requests`、`shop_holidays` |
| 決済 | `payments`（事業者列と事業者側 ID 列）、`webhook_events` |
| クーポン・ポイント | `coupons`、`coupon_redemptions`、`user_coupons`、`point_ledger`、`point_spend_allocations` |
| メール | `email_campaigns`、`email_jobs`、`email_templates`、同意記録、`mail_scenarios` 系（ステップメール）、`shipping_mail_outbox` |
| コンテンツ | `content_pages`、`home_sections` 系、`menu_items`、`notices` |
| 顧客・運用 | `customer_segments`、`inquiries`、`admin_audit_logs`、`ops_job_runs`、`shop_settings`、`tax_classes`、`tax_rates`、`postal_codes` |

マイグレーションの流儀です。

- `migrations/` に日時接頭辞つきの連番ファイルとして置き、
  sqlx の `migrate!` でバイナリに埋め込み、起動時に適用します。
- **適用済みファイルは編集しません。** 変更は常に新しいファイルの
  追加で行います（チェックサム検証に触れるためです）。
- 接続は2ロールに分かれます。マイグレーション実行用のオーナーと、
  実行時に使う最小権限のアプリ用ロールです。
- 新しいマイグレーションファイルを足したら、埋め込みを
  再コンパイルさせるために `app/src/lib.rs` に触れてから
  ビルドしてください（`migrate!` はコンパイル時にファイルを
  読み込むためです）。

## 7. 変更ガイド（どこを触るか）

| やりたいこと | 触る場所 |
|---|---|
| 決済事業者を足す | `services/payment_gateway.rs` のトレイトを実装し、クライアントを追加（`komoju_client.rs` / `stripe_client.rs` が手本）。`hosted_gateway` の選択肢と `payments.provider` の CHECK に事業者名を足す（内部の設計資料を参照） |
| 支払方法を足す | `models/payment.rs` の `PaymentMethod` と `payment_service::offered_methods`、チェックアウト画面 |
| バックグラウンド処理を足す | サービスに `start_worker` を作り、`server/src/background_tasks.rs` の `start_all` に1行登録する（`main.rs` は触らない） |
| 管理画面のページを足す | `controllers/admin/` にハンドラ、`resources/templates/admin/` にテンプレート、`routes.rs` に登録、権限ガードの対象に追加 |
| ストアフロントのページを足す | `controllers/storefront/`、`resources/templates/storefront/`、`routes.rs` |
| スキーマを変える | `migrations/` に新規ファイルを追加する（適用済みは編集しない） |
| 設定項目を足す | 非秘密は `configuration` クレートの型と `config.toml`、秘密は環境変数と `.env.example` |
| 利用者向け文言を足す・変える | `app/src/messages.rs` に集約する |
| メールシナリオを足す | 内部の設計資料のシナリオ／ステップ／登録モデルに従い、`scenario_service` とシードを追加 |
